# Threat model — WPGuard Nextcloud Backup (MVP)

Status: MVP, under active development. Security checks below were run
as part of build-and-test for each feature, then independently
re-verified by a separate security audit before that feature is marked
shippable — see `STATUS.md` for the audit history. That audit process is
not a substitute for your own review before production use on
infrastructure you depend on. See "Independent security audit" at the
end.

## Assets

1. Nextcloud app password (credential).
2. Full site database export (contains user password hashes, session
   tokens, any PII in posts/comments/users, plugin secrets stored in
   `wp_options`).
3. Full site file export (contains `wp-config.php` — DB credentials, auth
   salts; themes/plugins; media, which may include non-public uploads).
4. The backup archives at rest on Nextcloud.
5. WordPress admin capability to trigger backups / read settings.

## Actors

- **Site admin** (trusted, `manage_options`): intended operator.
- **Other authenticated WP users** (lower capability): must not reach any
  plugin action.
- **Unauthenticated web visitor**: must not reach any plugin action or file.
- **Network attacker** (on path between WP host and Nextcloud, or
  on-path within the shared host): sees only TLS-protected traffic if TLS
  verification holds.
- **Someone with read access to the WordPress database** (e.g., via a
  different vulnerability, or a hosting-provider insider): sees the stored
  app password (ADR 0002 documents this residual risk explicitly) and sees
  job metadata (never the DB/file archive contents themselves, those aren't
  stored locally after upload).
- **Someone with read access to the configured Nextcloud account/folder**:
  this is the intended backup consumer, but if that account is
  over-privileged (e.g., admin, or shared with other data), the full
  archive content is exposed to anyone with equivalent access — hence
  ADR's and the brief's insistence on a *dedicated, non-admin* Nextcloud
  account.

## STRIDE-style pass over the MVP surface

| # | Threat | Where | Mitigation in this build |
|---|---|---|---|
| T1 | CSRF triggering a backup or changing settings | `admin-ajax.php` actions, including `wpguard_nc_cancel_job` (added 2026-10-19) | `wp_verify_nonce` on every write action; nonce scoped per-form, checked server-side, action rejected (403 + logged) without it |
| T2 | Non-admin triggers backup or reads settings/secrets | same actions, including `wpguard_nc_cancel_job` (added 2026-10-19) | `current_user_can('manage_options')` checked on every action handler before any other logic; denied requests return 403 and are logged (sanitized, no secret echo) |
| T3 | Reflected/stored XSS via settings fields (URL, folder path, CA bundle path) | admin settings page render | All output escaped with `esc_html`/`esc_attr`/`esc_url` at render; all input sanitized (`sanitize_text_field`, `esc_url_raw`) and validated (URL scheme must be `https`, folder path restricted to a safe charset) on save |
| T4 | SQL injection in the DB exporter | `class-db-exporter.php` | Table/column identifiers come only from `SHOW TABLES`/`SHOW COLUMNS` against the live schema (never user input) and are backtick-quoted; all values are read via prepared `$wpdb->prepare` style parameter binding when filtering, never string-concatenated from request input |
| T5 | SSRF — plugin fetches an attacker-controlled internal URL | Nextcloud base URL setting | Base URL is admin-only (`manage_options`), not reachable by lower-privileged users or request parameters; URL must be `https`; this is an accepted admin-configurable *destination*, not a general-purpose fetcher (no feature lets a non-admin or a webhook influence the target). Documented residual risk: a malicious admin (already fully trusted in WordPress's model) could point it at an internal HTTPS service — out of scope, admins are already trusted |
| T6 | Path traversal / zip-slip on restore | restore runbook / any future restore tooling | Archive writer never writes paths containing `..` or absolute paths into the zip; restore runbook instructs extraction with a modern `unzip`/`ZipArchive` (both reject `..`-escaping entries) and the manual runbook explicitly tells the operator to verify extracted paths stay under the target root before use. Covered by an automated unit test asserting a crafted `../../evil.php` entry name is rejected by the archive writer at write time (defense in depth: reject at creation, not just at extraction) |
| T7 | Zip/archive bomb on restore or on verification read-back | verification step, restore | Read-back verification streams to a temp file with a byte-size ceiling check against the manifest's declared size *before* full download completes (abort if actual exceeds declared by more than a small tolerance); restore runbook warns to check available disk space against manifest-declared sizes before extracting |
| T8 | Credential disclosure via logs | `class-logger.php`, any error message | A single redaction routine (`Logger::redact()`) strips any string matching the stored app password (compared by value, not just key name) and any string matching common secret-shaped patterns before writing any log line, admin notice, or AJAX response. Unit-tested: logger given a string containing the live test app password emits a log line that does **not** contain it |
| T9 | Credential disclosure via the SQL/file archive itself | DB exporter, file inventory | The exporter explicitly excludes the plugin's own options row(s) that hold the app password/CA path from the `wp_options` table dump (row-level exclusion, not whole-table exclusion, since `wp_options` holds much else that must be backed up); file inventory excludes the plugin's own local staging/temp directory. **The security audit (2026-10-19) found this was incomplete**: when the admin uses ADR 0002's constant-override escape hatch, the credential lives in `wp-config.php`, which was archived verbatim — the backup that depends on the credential also contained it (H-02). Fixed: `wp-config.php` is redacted (credential-constant `define()` lines stripped) before archiving, regardless of whether the override is active, and `Settings::save()` now purges any stale `wp_options` copy once the constant takes over. Verified by an automated test: generate a backup, grep the resulting SQL export and every archived file for the literal app-password string — must not match |
| T10 | Credential disclosure via browser (settings page re-renders saved password) | settings page | Password field is always rendered empty/masked on load; saving a blank password field means "leave unchanged," never "clear it" — enforced server-side, not just UI convention |
| T11 | Man-in-the-middle due to disabled/weakened TLS verification | Nextcloud client | No code path sets `sslverify => false` (grep-enforced, see `tests/unit/NoInsecureTlsTest.php`); only mitigation available is a verified, admin-supplied private CA bundle (ADR 0007), never a bypass |
| T12 | False success — upload reported OK without real verification | transport/verification | ADR 0006: every part is read back and hashed; `COMPLETE.json` is the only success signal and is itself verified after upload; unit + integration tests assert a corrupted/truncated remote object is detected and the job is marked failed, not verified. **The security audit (2026-10-19) found a second path to false success**: the AJAX admin-UI polling and the WP-Cron fallback could both call `Job_Orchestrator::advance()` for the same job with no mutual exclusion, racing on the same checkpoint — producing a backup that was structurally corrupt (duplicated/lost table or zip entries) but whose locally-computed hash still matched what got uploaded, so it still passed verification (H-01). The WP-CLI path this plugin's own E2E test uses never hit this, since WP-CLI never schedules WP-Cron. Fixed with a non-blocking MySQL advisory lock (`GET_LOCK`/`RELEASE_LOCK` keyed by job_id) around the whole of `advance()`: a second caller that can't acquire the lock just reports current state instead of racing it. **2026-10-19**: a new `Job_Orchestrator::cancel()` admin override (JOB-05 manual recovery) was built and security-audit-reviewed against this same lock — it respects `try_lock()` and reports `lock_contended` (not success) if `advance()` holds it, verified live by `tests/e2e/run-e2e-cancel-lock-contention.sh` (a genuinely concurrent holder process + a canceller process, same shape as `run-e2e-lock-race.sh`). **Still open**: no regression test yet exercises concurrent AJAX+cron *advancement* directly (two `advance()` calls racing each other); current coverage there is still the existing single-process E2E drill plus code-level review — the new test covers `cancel()` vs `advance()` contention, not `advance()` vs `advance()` |
| T13 | A failed/interrupted run destroys the last good backup, or retention pruning deletes the wrong (too many, or still-needed) backups, or a fully-trusted-but-malicious/careless admin uses retention to destroy backup history | retention | MVP performed no deletion of any kind. **Phase 2 (2026-10-20)**: retention pruning (`Retention::prune()`) now exists, default **disabled** (`retention_count = 0`, keep-all) specifically so no plugin update or activation can silently start deleting backups — an admin must explicitly opt into a positive count. Only ever runs after a job is already marked `verified` (`Job_Orchestrator::maybe_prune_old_backups()`, called from `step_finalize()`), and a pruning failure is caught and logged, never flips a verified backup back to failed. Deletes oldest-first by lexicographic `backup_id` order among *verified* backups only (chronological by construction, since `backup_id` is timestamp-prefixed) — a folder must match the real `backup_id` format and carry a `COMPLETE.json` to count at all; a failed/interrupted job's folder is neither counted toward the keep-N total nor touched (**the follow-up security audit, 2026-10-20, RETENTION-2** — initially missed: such folders were silently counted, meaning fewer real backups survived than the configured count). The just-finished backup is always the newest verified one and therefore always kept, with no special-casing needed. Verified against a real Nextcloud account (not a mock): `tests/e2e/run-e2e-retention.sh` proves `keep=0` is a true no-op, `keep=N` deletes exactly the oldest excess among verified backups, a failed-job stub is never counted or touched, and a real end-to-end run through `step_finalize()` itself (not just a direct call to `prune()`) completes without the arity error described below. A deliberately interrupted job still leaves a prior `COMPLETE.json`-bearing backup folder untouched regardless of retention. **Same audit also found two implementation bugs that had silently disabled retention entirely**: `maybe_prune_old_backups()` called `Retention::prune()` with the wrong number of arguments (an `ArgumentCountError` in PHP 8, silently caught by its own try/catch — retention never actually ran in production despite passing a direct-call test of `prune()` alone) and `prune()`'s declared `: array` return type didn't match its `WP_Error` return path (also a PHP 8 `TypeError`, also silently caught) — both fixed, and the regression test now exercises the real `step_finalize()` call site specifically so this class of bug can't hide behind a direct-call-only test again (RETENTION-3/4). **Residual, accepted risk**: a fully trusted WP admin (already fully trusted in this plugin's threat model — see "Residual risks" below) could set `retention_count=1` and trigger a backup specifically to destroy prior backup history. Confirmed live against the real Nextcloud test server (2026-10-20): a WebDAV `DELETE` here lands in that account's own trashbin, not permanent erasure — meaningfully reduces, but does not eliminate, this risk (depends on that server's own trashbin retention/quota policy, which this plugin has no visibility into) |
| T14 | Public exposure of backup files or temp archives | local temp storage, Nextcloud folder | Local temp files are written under `wp-content/wpguard-nc-backup-tmp/` guarded by a generated `index.php` (empty, prevents directory listing) and a `.htaccess` deny-all (Apache only — no equivalent protection on Nginx). **The security audit (2026-10-19, L-01) found `cleanup_tmp()` previously ran only on the success path**; a failed job left partial `database.sql.gz`/`files.part-*.zip` under a `backup_id`-named directory indefinitely, directly web-accessible by URL on Nginx hosts (bounded by the 32-bit random suffix in `backup_id`, and the SQL dump already excludes the credential row, so practical exploitability was judged LOW, but the description was wrong). Fixed: `cleanup_tmp()` now also runs on the failure path |
| T15 | Archive bomb / resource exhaustion from a malicious or corrupted SQL/file component during restore testing | E2E harness | E2E harness runs inside disposable containers with no access to production resources regardless of outcome |
| T16 | Downgrade: admin accidentally points Nextcloud URL at plain `http://` | settings validation | Save-time validation rejects any scheme other than `https`; no setting exists to override this in MVP |
| T17 | Unattended WP-Cron-triggered state changes (Phase 2, 2026-10-20): the automatic stale-lock reaper and automatic scheduled backups both run with no request-level nonce/capability check, reachable (in the WP-Cron pseudo-cron sense) by any site visitor's page load | `Job_Orchestrator::reap_stale_lock()`, `run_scheduled_backup()`, both in `wpguard-nc-backup.php`/`class-job-orchestrator.php` | **the follow-up security audit, 2026-10-20**: correct as designed, not a gap — neither function accepts any request input of any kind (no `$_POST`/`$_GET` reach either one), so there is nothing for an unauthenticated visitor to inject; a nonce/capability check exists to gate *user-supplied input*, which doesn't apply to a cron callback with none. The reaper's only observable effect (marking a job `failed`) is the same state transition the existing capability-gated Cancel button already performs. `run_scheduled_backup()` only starts a job if `Settings::has_credentials()` and reuses `create_job()` unchanged. LOW-JOB05-1 (same audit): the reaper's hourly cron widens the pre-existing LOW-R2 `wait_timeout`-lock-drop condition's practical surface (a second actor beyond a concurrent `advance()` call could now acquire a dropped lock), but the outcome stays bounded to the job being marked `failed`, never incorrectly `verified` (`advance()`'s terminal-state check prevents any further transition past a job already marked failed out from under it) |
| T18 | Self-hosted update feed (Phase 2, 2026-10-20): a malicious or compromised update source could get WP to download and install an attacker-controlled package with full plugin-code execution — the highest-impact category this plugin's own feature set can introduce | `Update_Checker`, polls `api.github.com` (public, unauthenticated GET) for the repo's latest Release | Package source is `github.com/ItsMNLOP/wpguard-nc-backup` only — same repo and account that already controls the plugin's own source code, so this introduces no *new* trusted party; TLS to `api.github.com` is handled by WP's own `wp_remote_get()` (standard cert verification, not overridden — see T11's no-`sslverify`-bypass guarantee, which applies here too). **Fail-closed by construction**: an update is only ever offered when the release carries an explicit `.zip` asset (`Update_Checker::select_package_asset()`, name must start with the plugin slug and end in `.zip`) — never GitHub's auto-generated zipball, which contains the whole repo (including `tests/`, `.github/`, `docs/`) rather than just the plugin folder, so using it as the install package would be wrong even with no attacker involved at all; `tests/e2e/run-e2e-update-checker.sh` Case C proves a newer-but-asset-less release is never offered. Release body text is rendered in the "View details" popup through `wp_kses_post()` before display, not trusted as pre-sanitized HTML. No request input of any kind reaches `check_for_update()`/`plugin_info()` — the only data path in is the TLS-authenticated GitHub API response (corrected wording, the security audit 2026-10-20: "not reachable by an unauthenticated visitor's *request*" is the precise claim; WP's own pseudo-cron, which any page load can trigger, can still be what *calls* these handlers — it just supplies no attacker-controlled input to them). **The security audit, 2026-10-20 (H-001, BLOCKED until fixed): this plugin has no WordPress.org listing, and before this audit had no `Update URI:` header either — WP core would still query `api.wordpress.org` for the unclaimed `wpguard-nc-backup` slug and could populate this same update transient with a slug-squatter's entry, which every early-return in `check_for_update()`/`plugin_info()` would then have passed through untouched (proven exploitable with no GitHub or database access: register the slug on WP.org, publish a higher version, wait for the next pseudo-cron-triggered check).** Fixed three ways: added the `Update URI:` header (WP 6.1+, tells core to skip the WP.org query for this plugin entirely); `check_for_update()` now unconditionally `unset()`s any existing transient entry under this plugin's basename before deciding whether to replace it, so no other source can survive under our slug regardless of header support; `plugin_info()` now returns a `WP_Error` instead of passing through whatever a prior filter (potentially WP.org) already produced when no GitHub release is available. **L-001 (LOW, same audit)**: a cached or API-sourced package URL wasn't checked against this repo's own release path before being trusted — a host-only check would still accept a different repo's release asset, and anyone with direct `wp_options` write access (already a serious compromise on its own) could plant an arbitrary URL in the cached transient. Fixed with `Update_Checker::is_trusted_package_url()`, a prefix match against `https://github.com/ItsMNLOP/wpguard-nc-backup/releases/download/`, applied at cache-read and both emission points (`check_for_update()`'s transient and `plugin_info()`'s `download_link`). Regression tests: `tests/unit/UpdateCheckerTest.php` (the trust-check helper) and `run-e2e-update-checker.sh` Cases E/F (a simulated pre-existing WP.org entry, and a cached different-repo package URL). **the security re-verification, 2026-10-20**: H-001 confirmed cleared (also found and corrected a misstatement in this project's own commit message — the `Update URI:` header does NOT stop this plugin's slug from being sent to `api.wordpress.org` in WP's update-check request; it only gates a different fallback filter that fires only if WP.org returned no update at all. The actual H-001 defense is `check_for_update()`'s `unset()`, confirmed live by replaying a mocked WP.org squatter response through the real `wp_update_plugins()` and observing it stripped). **L-001 was still BLOCKED**: `is_trusted_package_url()`'s `strncasecmp()` prefix check was proven bypassable with a path-traversal tag segment (`../../../../other-repo/...`), since a prefix match never inspects what follows it — confirmed live with a real HTTP 302 to an unrelated public repo's release asset. Fixed by replacing the prefix check with a full anchored regex: the tag segment must start with an alphanumeric character (excluding `.`/`..`), neither segment may contain `%`, `?`, `#`, `@`, `\`, or `/`, and `\z` (not `$`) anchors at the true end of the string so a trailing newline can't smuggle anything past the check. 6 new unit tests (traversal, URL-encoded traversal, mixed-encoding traversal, query-string injection, fragment injection, trailing newline) and a new E2E Case G (the exact proven-live bypass shape, confirmed never offered). Residual: whoever can push a Release to this repo (today, the same single GitHub identity that can push commits to `main` — see the branch-protection discussion in `STATUS.md`) can cause any site running this plugin to install arbitrary code on its next update check; this is the same blast radius as that identity already has by pushing to `main` directly (nothing in this feature expands who is trusted, only how an already-trusted change reaches installed sites). **Non-blocking recommendation (the security audit)**: once the CI bash port (item 10) can build release assets automatically, also publish a SHA-256 digest alongside the `.zip` and verify it via `upgrader_source_selection` before install, for integrity independent of TLS alone — not built yet, no CI to automate it with. |

| T19 | Incremental file backups (Phase 2, 2026-10-20): a chain-based optimization — skipping re-upload of unchanged files by referencing an earlier backup's bytes instead — introduces its own failure class distinct from anything full-backup-only MVP had: a partial restore that looks complete, a deleted file resurrected on restore, or retention pruning breaking an in-use chain | `class-backup-chain.php`, `step_export_files()`/`step_finalize()` in `class-job-orchestrator.php`, chain-aware `Retention::prune()` | **Not a diff/patch chain by design** — every manifest's `files` list is always the complete, resolved current state (see `class-backup-chain.php`'s docblock), never a delta applied on top of a previous restore. This eliminates deletion-resurrection as a risk class entirely: a deleted file has no entry in any later manifest (it's simply absent from that run's filesystem walk), so a restore driven by the latest manifest alone — the only restore path this document or any test exercises — can never bring it back, including a backdoor file an admin deliberately removed. **Partial-restore-looks-complete is addressed by moving validation to backup-creation time, not restore time**: `Backup_Chain::plan()` confirms the previous chain backup's manifest and every part it transitively references still exist on the real server *before* trusting any of it (a PROPFIND per distinct referenced part) — any gap found there (manifest unreadable, a referenced part missing) falls back to taking a full backup for that run instead, decided in `step_init()` before any file is skipped, never discovered too late to recover. **Precision correction (the security audit, 2026-10-20)**: this PROPFIND is an *existence* check (plus a reported content-length), not a content/hash check — it confirms a referenced ancestor part is still there, not that its bytes are still intact. Content-level integrity of an ancestor part was established once, at its own original upload time (the same full read-back + sha256 verification every part always gets before its own backup is ever marked `verified`); a server-side bit-rot/corruption event on an already-verified ancestor part after the fact would not be caught at `plan()` time, only later, at actual restore time, via the per-file `sha256` fields in `files[]`. The HIGH/MEDIUM findings from the same audit (below) addressed a different, more severe gap in the opposite direction — files silently missing from a part *this job itself* just produced, never making it into `verified` at all.

**The security audit, 2026-10-20 — BLOCKED, then fixed same-day. HIGH-ZIP-1**: `ZipArchive::close()`'s return value was previously discarded entirely by `Archive_Writer::close_part()`. Proven live: libzip rolls back the *entire* pending batch — every `addFile()` since the last successful `close()`, not just the file whose source actually disappeared — if any one added file's source becomes missing or unreadable before `close()` runs (a cache-busting script, log rotation, a concurrent deploy, a disk-full condition, or the JOB-05-documented hard-kill case). The checkpoint had already recorded those files as archived (per-file commit happened before the batch-ending `close()`), so a job could reach `verified` with files silently absent from the uploaded part — exactly the "looks complete, isn't" failure this feature's own threat model above calls the worst case. Fixed: `close_part()` now returns `true|WP_Error`; every call site checks it; `step_export_files()` restructured so a file is only ever committed into the persisted checkpoint (`resolved_files`/`files_remaining`) once the `close()` that makes its archive entry durable has already succeeded, never merely because `addFile()` returned true. A new pre-upload check, `verify_own_parts_contain_claimed_files()` (called from `step_package_manifest()`, before any upload begins), opens every part this job itself produced and confirms every file the manifest claims lives there is actually `locateName()`-able inside it — a backstop the existing part-level sha256 read-back could never provide, since a part missing entries still round-trips its own (smaller) bytes perfectly. **MEDIUM-ZIP-2 (same audit)**: a part holding only zero-byte files (real: empty `.log`/`.gitkeep`/sentinel files) after a size-based rollover could read `current_part_bytes === 0` at end-of-step and never get finalized, uploaded, or become restorable, while still being referenced by `resolved_files`. Fixed by also tracking `current_part_file_count` and finalizing whenever either is non-zero. **MEDIUM-RESTORE-1 (same audit)**: `docs/restore-manual.md` step 1a had three gaps — ancestor parts sharing the same `files.part-NNNN.zip` name across different `source_backup_id`s with no collision-safe naming instruction, no explicit warning against whole-archive `unzip` of an ancestor part (which would resurrect deleted files — the exact risk this feature's main design claims to eliminate, undermined by an under-specified manual procedure), and no instruction to verify extracted files against their manifest `sha256`. Fixed — see step 1a's revised text. **Three LOWs, also fixed**: `Backup_Chain::record_result()` re-read `base_created_at` from options storage rather than using the value `plan()` already captured — fixed by threading it through `$chain_plan`; `Retention::prune()`'s fail-closed abort-on-unreadable-manifest had no visible symptom beyond a per-job log line — fixed with a persistent admin notice (`Job_Orchestrator::RETENTION_ERROR_OPTION`), cleared automatically the next time pruning succeeds; `Archive_Writer::open_part()`'s `file_exists()` ternary was dead code (`0 ?: CREATE` always evaluates to `CREATE`) — harmless in practice but rewritten for clarity. All fixes verified: 62/62 unit tests, the full incremental E2E suite, and the existing retention/scheduling/stale-lock/main-restore E2E suites all green.

**the security re-verification, 2026-10-20**: found the HIGH-ZIP-1 fix had introduced its own new gap (**NEW-HIGH-1**) — the unchanged-file (incremental-skip) fast path in `step_export_files()` committed `$cp['files_remaining']` immediately, which by that point could already be missing an earlier-in-the-same-batch *changed* file still sitting uncommitted in the archive path's `$pending` list (archived into the zip, not yet durably closed). A crash in that narrow window (most plausibly during the `close()` call itself, the single longest operation in the batch) would persist a checkpoint where that changed file exists in neither `files_remaining` nor `resolved_files` — the same silent-omission failure class as the original finding, introduced by its own fix. Fixed: the skip path now queues into the same `$pending` list as the archive path, committed only at the same two existing flush points (a successful mid-batch rollover close, or the end-of-batch close). Also found **MEDIUM-RESTORE-2**: `wp-config.php` is a normal entry in every manifest's `files[]` list (`Inventory::enumerate()` includes it like any other file), so step 1a's generic extraction loop would have blindly overwritten the restore target's `wp-config.php` with the *source* site's DB credentials, bypassing step 6's RST-04 reconciliation entirely for any incremental restore. Fixed: step 1a's extraction and verification loops now explicitly exclude `wp-config.php`, routed instead through step 6's existing selective-merge procedure (a new step 1a.4a). Two further LOWs fixed as defense in depth: `verify_own_parts_contain_claimed_files()` now also compares each entry's archived size against the manifest's claimed size (`ZipArchive::statName()`), not just presence; the unit test proving HIGH-ZIP-1's live rollback behavior had one assertion conditionally skippable if a later `ZipArchive::open()` happened to fail — rewritten as an unconditional two-phase proof. Second re-verification re-sent. The global `format_version` bump (1 -> 2) additionally means any restore tooling written against the pre-incremental docs refuses outright rather than silently restoring only the files physically present in one backup's own folder. **Retention-breaks-chain was flagged as the default outcome, not an edge case, during design review** (naive oldest-first pruning always deletes a chain's base first, since it's always the oldest) — `Retention::prune()` now computes the full transitive set of `source_backup_id`s every kept backup's own manifest depends on and never deletes anything in that set, verified live (not just by direct-call test, same RETENTION-3-era lesson) by `tests/e2e/run-e2e-incremental.sh`'s chain-aware-retention case, which confirms a backup still depended on by a kept backup survives even though it's the oldest by name, while a fully-superseded backup in between is still correctly reclaimed. **Residual, accepted risk**: the (size, mtime) unchanged-check is cheap by design (reading/hashing every file to detect changes would erase most of the performance win this feature exists for) but has a known blind spot — a file whose content changed while its mtime was preserved (by a deploy tool, or deliberately by an attacker who already has filesystem write access) would be missed and its old bytes would keep being referenced. Bounded, not eliminated, by the forced periodic full backup (every `wpguard_nc_incremental_max_chain` backups or `wpguard_nc_incremental_max_chain_days` days, whichever comes first, both default 7) — this caps the exposure window to at most one chain's length, not indefinitely. An attacker who already has filesystem write access to plant such a file has threat-model-equivalent access to simply modify the live site directly (see "Residual risks" below — a fully trusted WP admin/filesystem is already fully trusted), so this isn't a new privilege escalation, only a detection gap within an already-assumed-trusted boundary. Default is **off** (opt-in), same reasoning as scheduling/retention: no existing site's backup/restore story changes unless an admin explicitly turns it on. |

| T20 | One-click restore (Phase 2, RST-04, 2026-10-20): the highest-impact feature this plugin can ship — an in-place restore that goes wrong can destroy the live site it's running on, including its own ability to keep running at all | `class-restore-orchestrator.php` | Built only with the owner's explicit approval given the brief's own gate on this specific feature ("no one-click destructive restore," "threat review and explicit owner approval" required) — a general Phase 2 autonomy grant does not cover it; see STATUS.md for that decision. **Two-phase design, not one**: `restore_acquire`/`restore_preflight` are entirely read-only (fetch, integrity-verify everything into staging, run every failable check) before `restore_apply_db` -- the actual point of no return -- ever begins; the database import lands in shadow-prefixed tables, never live ones directly, and the final swap is one atomic multi-table `RENAME TABLE`, never a row-by-row or table-by-table sequence that could be left half-done. **Found live, during this feature's own E2E testing against a real production backup (not a synthetic fixture) — the plugin's own self-destruction risk was real, not theoretical**: restoring an older backup quarantined the plugin's OWN currently-running files (added after that backup was taken), breaking its autoloader mid-restore, and separately, the backup's own `wp-config.php` silently overwrote the target's DB credentials. (MEDIUM) `step_bundle_local()` allocated a fresh token/directory on every call with no check for one already in progress, so a process killed mid-assembly orphaned its partial directory forever while the next retry silently started another, unbounded for as long as an admin's tab kept polling; fixed by persisting the token into the checkpoint and reusing it (wipe-and-rebuild, not re-allocate) on re-entry, a hard 3-attempt cap, and a `disk_free_space()` precheck. Three LOW findings closed a failed download job still contacting Nextcloud for its diagnostic log, `get_latest_verified()` surfacing a download-only job as the site's standing "last verified backup," and a swept bundle's checkpoint not being cleared (resurfacing a dead download link) -- plus a dedicated nonce for the download link, which previously reused the same nonce shared by every other action on the page, sitting in a navigable GET URL (browser history, server logs, Referer headers). All nine fixed same-day per standing instruction; 127/127 unit tests (10 new), full 13-script E2E regression re-run clean. **Re-verification found one new MEDIUM, ship-blocking**: the redaction regex's `.*?` (shared by both the original app-password/CA-bundle redaction and the new DB-credential one) is non-greedy and matches only up to the *first* `);` anywhere in the value -- proven live, a credential containing its own literal `);` fragment (plausible on hosts that generate passwords from the full printable-ASCII set) left everything after that point unredacted, AND simultaneously defeated the fail-closed `strpos()` re-check downstream, since that check searches for the *full* secret string, no longer present once part of it was consumed by the partial match -- a redaction failure that silently looked like success. Fixed by replacing `.*?` with a real quoted-string-literal match (`Settings::quoted_string_value_pattern()`, escape-aware, both quote styles, written as a nowdoc to avoid manually counting PHP-string-escape-of-regex-escape backslashes), confirmed directly against the exact proof case before trusting it. Two LOW findings in the same pass: `create_restore_job()` had no advisory lock at all (proven live -- a backup and a restore could run concurrently), fixed by sharing the same lock (extracted into `Job_Orchestrator::create_job_lock_name()`) so a backup-start and a restore-start now serialize against each other too; and the lock name was a bare static string that would contend with an unrelated site sharing the same MySQL server on shared hosting, fixed by namespacing it with this site's own `site_id`. 130/130 unit tests (3 more new), full regression re-run clean again (this round touched `create_restore_job()` too, so the restore-touching suites were back in scope). **Second re-verification: CLEAR TO SHIP.** One more mechanism surfaced and was deliberately accepted rather than fixed: a `define()` value built from string concatenation (`define('DB_PASSWORD', 'abc' . 'def');`) defeats both the regex (concatenation isn't a single string literal) and the fail-closed check (the runtime-joined value never appears as one contiguous substring in the source text either) -- folded into the pre-existing, already-accepted `LOW-R1` gap (`const` syntax) rather than opened as a separate finding, on the same basis: no real `wp-config.php` from any mainstream WordPress installer or hosting panel has ever been observed defining a credential constant via string concatenation. Also confirmed: this feature introduces no new advisory-lock concurrency surface beyond the pre-existing, already-documented `T12` gap -- download-generation steps run through the same `advance()`/lock mechanism as every other step, and the TTL sweep is a non-lock-interacting cron callback. Zero open HIGH/MEDIUM findings across all three rounds. |

## Explicitly out of scope for MVP (and why)

- Encryption at rest of the archive content: NFR-04/Phase 5 — "never invent
  cryptography" and no key-management story exists yet. Documented as a
  limitation: anyone with legitimate access to the Nextcloud destination
  account can read the raw backup content (same as TRN transport once
  stored — Nextcloud's own at-rest protections, if any, apply, not the
  plugin's).
- Multi-tenant/multisite isolation (multisite explicitly out of scope —
  parked in backlog, `STATUS.md` 2026-10-20, no multisite target exists
  to build or test against).

**No longer out of scope as of 2026-10-20 (Phase 2)**: WP-Cron-triggered
unattended runs now exist (automatic stale-lock recovery, automatic
scheduling) — see T17.

## Residual risks accepted for MVP, with owner-visible documentation

- App password at rest in `wp_options` (ADR 0002) unless the operator uses
  the constant override.
- No at-rest encryption of the uploaded archive (NFR-04).
- A fully trusted WordPress admin remains fully trusted (standard WordPress
  threat model; this plugin does not attempt to defend against its own
  administrator).

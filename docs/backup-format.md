# Backup format specification (manifest schema v1)

Status: MVP, version `1`. This document is the contract restore tooling and
future plugin versions must honor (MNT-04): old archives must remain
restorable even as the plugin evolves. Any breaking change to this schema
requires a new `format_version`, a documented migration/compatibility note
here, and restore tooling that detects an unsupported future version and
fails safely rather than guessing.

## Remote layout

```text
/<configured-folder>/<site-id>/
  backups/<backup-id>/
    manifest.json
    database.sql.gz            (or database.part-NNNN.sql.gz if split)
    files.part-0001.zip
    files.part-0002.zip
    ...
    COMPLETE.json               <- written LAST, only after all of the above verify
  staging/<backup-id>/...       <- used during upload, never trusted as a finished backup
```

- `<site-id>`: stable, filesystem/URL-safe identifier derived from the site's
  home URL host plus a short random suffix generated once and persisted
  locally (so re-installing the plugin on the same site keeps backing up to
  the same site folder; a different site never collides). Example:
  `example-com-7f3a9c`.
- `<backup-id>`: `YYYYMMDDTHHMMSSZ-<8 random hex chars>`, UTC, e.g.
  `20261019T153245Z-4b1e9a2f`. Sortable lexicographically, collision-safe.

## `manifest.json` (schema v1)

```json
{
  "format_version": 1,
  "backup_id": "20261019T153245Z-4b1e9a2f",
  "site_id": "example-com-7f3a9c",
  "created_at_utc": "2026-10-19T15:32:45Z",
  "plugin_version": "0.1.0",
  "generator": "wpthistle-backup-restore",
  "source": {
    "wp_version": "7.1",
    "php_version": "8.3.14",
    "db_server": "mariadb",
    "db_version": "11.4.4",
    "table_prefix": "wp_",
    "home_url": "https://source.example.test",
    "site_url": "https://source.example.test"
  },
  "consistency": "best-effort-live-snapshot",
  "scope": {
    "database": { "included": true, "tables": ["wp_posts", "..."] },
    "files": {
      "included_roots": ["wp-content", "wp-config.php", ".htaccess"],
      "excluded_patterns": ["wp-content/cache/**", "wp-content/wpthistle-backup-restore-tmp/**"],
      "excluded_external_note": "Files outside the WordPress document root, and any symlink targets outside the site root, are not included. See docs/restore-manual.md."
    }
  },
  "components": [
    {
      "path": "database.sql.gz",
      "kind": "database",
      "bytes": 1048576,
      "sha256": "…64 hex chars…",
      "part": 1,
      "parts_total": 1
    },
    {
      "path": "files.part-0001.zip",
      "kind": "files",
      "bytes": 67108864,
      "sha256": "…",
      "part": 1,
      "parts_total": 2
    }
  ],
  "tables_metadata": [
    {
      "name": "wp_posts",
      "row_count": 42,
      "ordering_strategy": "keyset-primary-key",
      "primary_key": "ID"
    }
  ],
  "warnings": []
}
```

Rules:
- **No secrets, ever.** The manifest generator has no access to the
  credential object at all (enforced by not passing it into the manifest
  writer's constructor), not just a redaction pass.
- `sha256` is computed locally from the exact bytes written to the part file
  before upload, and re-verified against a post-upload read-back hash
  (ADR 0006) — the manifest records the *authoritative, locally computed*
  value; the read-back is a check against it, not a second source of truth.
- `ordering_strategy` is one of `keyset-primary-key`,
  `keyset-composite`, or `unordered-full-scan` (ADR 0005); the latter always
  pairs with a `warnings[]` entry naming the table.
- Unknown future `format_version` values MUST cause restore/verification
  tooling to stop with an explicit "unsupported format version N, this tool
  supports up to M" error — never attempt a best-effort parse.

## `COMPLETE.json`

```json
{
  "format_version": 1,
  "backup_id": "20261019T153245Z-4b1e9a2f",
  "completed_at_utc": "2026-10-19T15:41:02Z",
  "manifest_sha256": "…sha256 of manifest.json's bytes, computed and verified same as any component…",
  "verification": "read-back-sha256"
}
```

`COMPLETE.json` existing (and itself passing a PROPFIND existence+size check,
and ideally a content read-back) is the **only** signal that a backup is
`verified`. Its absence means the backup is at best `uploaded-unverified` and
must never be presented to the operator as a success.

## Database export format

Plain-text SQL (`.sql`, gzip-compressed as `.sql.gz`), generated by the
plugin's own exporter (ADR 0005) — not a shelled-out `mysqldump` call (brief
NFR-05: no shell dependency on shared hosting). Structure:

```sql
-- wpthistle-backup-restore database export
-- format_version: 1
-- generated_at_utc: 2026-10-19T15:33:01Z
SET NAMES utf8mb4;
SET FOREIGN_KEY_CHECKS=0;

-- Table: wp_posts
DROP TABLE IF EXISTS `wp_posts`;
CREATE TABLE `wp_posts` ( ... );        -- verbatim SHOW CREATE TABLE output
INSERT INTO `wp_posts` (`ID`, ...) VALUES (1, ...), (2, ...);  -- batched, keyset-ordered
...

SET FOREIGN_KEY_CHECKS=1;
```

Restorable with a plain `mysql <target_db < database.sql` — no plugin
required to read it (RST-01).

## File archive format

Standard ZIP (`ZipArchive`), relative paths from the WordPress root, e.g.
`wp-content/themes/twentytwentyfour/style.css`. No absolute paths, no `..`
segments (enforced at write time, see threat model T6). `wp-config.php` is
included at its root-relative path; the archive writer never substitutes or
redacts its contents (it contains DB credentials needed for restore context,
but the *Nextcloud app password is not in wp-config.php* in MVP since
credentials are stored in `wp_options`, ADR 0002 — if the constant-override
path is used instead, that constant line IS present in the archived
`wp-config.php`, which is expected and documented: it's the admin's own
server file, the same as any other secret already in that file).

## Compatibility policy

- A `format_version` bump is required for any change that is not purely
  additive-and-ignorable (e.g., adding an optional manifest field is fine
  without a bump; changing what `sha256` is computed over, or changing the
  remote layout, requires a bump).
- Restore tooling bundled with any future plugin version must be able to
  read every `format_version` that plugin version's own backups could have
  produced, plus at least one prior major version back, per MNT-04/MNT-20.
  MVP ships only `format_version: 1`, so this policy has nothing to prove yet
  — it is recorded here so the first future bump inherits the obligation.
